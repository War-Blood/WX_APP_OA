## 一、背景

此前已对区域分布做过两轮修复（省份下钻三路径查人、非标准区域过滤、日期口径统一），但经排查发现**跨省去重逻辑仍有根本缺陷**，导致面板人数与下钻人数不一致。需重写需求文档厘清逻辑后再动手。

## 二、现有问题清单

### P0：跨省去重 — 面板人数 ≠ 下钻人数（核心Bug）

**现象**：面板上广东省显示 2 人，点开广东省下钻弹窗显示 3 人。

**根因**：`getAreaDistribution()` 的 `personMap` 以 `uid` 为唯一 key，同一个人在多个省份出现时，只保留第一次处理到的省份。

```
数据示例：
  报告 A：张三提交于广东省  → personMap[张三] = { province: "广东" }
  报告 B：李四提交于广西省，workers="张三"
          → personMap[张三] 已存在，同日不覆盖 → 丢弃

结果：
  面板：广东 2 人、广西 1 人（张三只计在广东）
  点开广西下钻：getProvinceWorkers('广西') 单省查询，找到张三 → 显示 2 人
  → 面板说 1 人，下钻说 2 人，对不上！
```

**影响范围**：
- 每个省份的 `count`（人数）偏少
- `workers` 列表缺人
- `projects` 集合缺项目

### P1：两个函数逻辑重复但实现不同

| 维度 | `getAreaDistribution` | `getProvinceWorkers` |
|------|----------------------|---------------------|
| SQL 范围 | 全表查所有省份 | `WHERE area LIKE 'X-%'` 单省 |
| 去重 key | `uid`（跨省全局） | `uid`（省内，天然正确） |
| 用户信息 | 仅查 `is_field_worker=1` | 从报告的 `user_id` 动态加载 |
| month 参数 | 接受但**忽略** | 接受但**忽略** |

两个函数各写一套逻辑，排查问题时容易顾此失彼。

### P2：前端传参混乱

```js
// stats.vue — 加载区域分布面板（不传 month，正常）
loadAreas() → reportApi.getAreaDistribution() → POST /api/stats/area-distribution { month: undefined }

// stats.vue — 省份下钻（传了 workTypeMonth，与区域分布无关）
openProvinceDrill(p) → reportApi.getProvinceWorkers(p.name, workTypeMonth.value)
                     → POST /api/stats/province-workers { province, month: "2026-06" }
```

后端 `getAreaDistribution` 和 `getProvinceWorkers` 都无视 `month` 参数、固定查昨日，所以传什么不影响结果。但 `workTypeMonth` 是工作类型分布 Tab 的月份选择器，跟区域分布毫无关系，语义混乱。

### P3：非 field_worker 用户信息缺失

`getAreaDistribution` 构建 `uidToInfo` 时只查 `is_field_worker = 1`：
```sql
SELECT id, nickname, user_name, worker_code FROM users
WHERE is_field_worker = 1 AND deleted_at IS NULL
```

如果 admin 代填了报告，其用户名可能为空（不在 field_worker 名单中），面板上显示空白。

### P4：同一人多条同日同省日志 → 只取第一条的 project

`addPerson` 在日期相同时不覆盖，但会用 `projects.add(project)` 追加。这部分逻辑是对的。但如果三条路径的处理顺序不同，project 归属可能不一致。

## 三、正确的业务逻辑（需求定义）

### 3.1 一个省份可以有哪些人？

某省的人员来源有三条路径（现有逻辑，保持不变）：

| 路径 | 说明 | 示例 |
|------|------|------|
| ① 直接提交人 | 自己提交了该省的公出日志 | 张三提交日志 area="广东省-广州市" |
| ② 关联表代填 | `daily_report_workers` 表中被代填到该省 | 李四代填，关联表记录 worker_uid=王五 |
| ③ workers 文本匹配 | 报告的 `workers` 字段中被列名 | 报告 workers="赵六、钱七"，匹配到 uid |

**规则**：只要满足任一路径，该人就属于这个省份。

### 3.2 一个人能同时出现在多个省份吗？

**能**。同一个人同日可能参与多个省份的工作：

- 自己提交了 A 省日志，同时被列在 B 省报告的 workers 中
- 被多个提交人在不同省份代填

**规则**：不跨省去重。人在几省出现就计在几省。

### 3.3 面板人数与下钻人数必须一致

| 位置 | 数据来源 | 要求 |
|------|---------|------|
| 面板 | `getAreaDistribution` 返回的 `count` 和 `workers` | count = workers.length |
| 下钻弹窗 | `getProvinceWorkers` 返回的 `workers` | workers.length = 面板 count |

**规则**：对同一个省份，面板人数 = 下钻人数，永久一致。

### 3.4 数据范围

- **只看昨日**（当前设计，不变）
- 仅统计 `status = 'approved'` 且 `report_type != 'office'` 的日志
- area 不含 `-` 的（GPS 定位等非标准格式）过滤掉

## 四、修改方案

### 4.1 后端：修复去重粒度（核心改动）

**文件**：`backend/src/core/services/stats.service.js`

**改动点**：`getAreaDistribution()` 函数中，`personMap` 的 key 从 `uid` 改为 `${uid}_${province}`。

```js
// 改前：
const personMap = {}; // key = uid → 跨省冲突
const addPerson = (uid, date, area, project, userName) => {
    if (!personMap[uid] || d > personMap[uid].dateStr) {
      personMap[uid] = { province, ... };
    }
};

// 改后：

    const province = area.split('-')[0];
```

### 7.2 `getProvinceWorkers` — 补全 uidToInfo

**文件**: `backend/src/core/services/stats.service.js` (第 868-961 行)

问题：只查了 `reports` 的 `user_id` 列表来加载用户信息，但 workers 文本匹配到的 uid 可能不在这个列表中。

```diff
  // 预加载用户信息
  const uidToInfo = {};
+ // 收集所有可能的 uid：直接提交人 + 待匹配的 workers
+ const allUids = new Set(reports.map(r => r.user_id));
+ 
+ // 预扫描 workers 文本，提前收集 uid 用于批量查用户信息
+ // （目前 nameToUid 在后面才构建，导致部分用户信息缺失）
+ 
  if (uids.length > 0) {
    const userRows = await db.query(
      `SELECT id, nickname, user_name, worker_code FROM users WHERE id IN (...)`,
      uids
    );
    ...
  }
```

实际上 `getProvinceWorkers` 的 `uidToInfo` 构建有两步：
1. 先查 `reports` 的 `user_id` 们
2. 再查 `subs` 的 `user_id` 们（补漏）

但第三步 workers 文本匹配时，`nameToUid` 是从 `uidToInfo` 反推出的——这就形成了循环依赖：只有已经加载了用户信息，才能通过名字匹配到 uid，才能补全该 uid 的用户信息。

**修复**：workers 文本中可能提到的用户，如果不在 `uidToInfo` 中，也要批量加载：

```diff
  // 路径3: workers 文本字段匹配
  const nameToUid = {};
  Object.entries(uidToInfo).forEach(([uid, info]) => {
    if (info.userName) nameToUid[info.userName] = Number(uid);
  });
+ 
+ // 补充：workers 文本中可能包含尚未加载的用户
+ const extraUids = [];
  reports.forEach(r => {
    if (!r.workers) return;
    const names = r.workers.split(/[、,，\s\/\n]+/).map(s => s.trim()).filter(Boolean);
    names.forEach(name => {
      const uid = nameToUid[name];
-     if (uid && uid !== r.user_id) addPerson(uid, r.area, r.project);
+     if (uid && uid !== r.user_id) {
+       addPerson(uid, r.area, r.project);
+     } else if (!uid && name && !nameToUid[name]) {
+       // 名字尚未匹配到 uid，记录下来批量查询
+       extraUids.push(name);
+     }
    });
  });
+ 
+ // 批量加载 workers 文本中新出现的用户
+ if (extraUids.length > 0) {
+   const extraRows = await db.query(
+     `SELECT id, nickname, user_name, worker_code FROM users
+      WHERE (nickname IN (${extraUids.map(() => '?').join(',')})
+             OR user_name IN (${extraUids.map(() => '?').join(',')}))
+            AND deleted_at IS NULL`,
+     [...extraUids, ...extraUids]
+   );
+   extraRows.forEach(u => {
+     if (!uidToInfo[u.id]) {
+       uidToInfo[u.id] = { userName: u.nickname || u.user_name || '', workerCode: u.worker_code || '' };
+     }
+     const n = (u.nickname || u.user_name || '').trim();
+     if (n && !nameToUid[n]) nameToUid[n] = u.id;
+   });
+   // 重新处理之前未匹配的名字
+   reports.forEach(r => {
+     if (!r.workers) return;
+     const names = r.workers.split(/[、,，\s\/\n]+/).map(s => s.trim()).filter(Boolean);
+     names.forEach(name => {
+       const uid = nameToUid[name];
+       if (uid && uid !== r.user_id) addPerson(uid, r.area, r.project);
+     });
+   });
+ }
```

## 八、SQL 验证查询

部署后可在服务器上直接执行以下 SQL 交叉验证：

```sql
-- 1. 查看昨日所有报告的区域分布（原始数据）
SELECT dr.area, dr.user_id, u.nickname, dr.project, dr.workers
FROM daily_reports dr
LEFT JOIN users u ON dr.user_id = u.id
WHERE dr.status = 'approved'
  AND dr.report_type != 'office'
  AND dr.area IS NOT NULL AND dr.area != ''
  AND dr.report_date = CURDATE() - INTERVAL 1 DAY
ORDER BY dr.area;

-- 2. 检查"同一人出现在多省"的情况
SELECT u.nickname, dr.area
FROM daily_reports dr
JOIN users u ON dr.user_id = u.id
WHERE dr.status = 'approved'
  AND dr.report_type != 'office'
  AND dr.area LIKE '%-%'
  AND dr.report_date = CURDATE() - INTERVAL 1 DAY
GROUP BY u.id, SUBSTRING_INDEX(dr.area, '-', 1)
HAVING COUNT(DISTINCT SUBSTRING_INDEX(dr.area, '-', 1)) > 1;

-- 3. 检查 workers 文本中跨省的人
SELECT dr.area, dr.workers, u.nickname AS submitter
FROM daily_reports dr
JOIN users u ON dr.user_id = u.id
WHERE dr.status = 'approved'
  AND dr.report_type != 'office'
  AND dr.workers IS NOT NULL AND dr.workers != ''
  AND dr.report_date = CURDATE() - INTERVAL 1 DAY;

-- 4. 验证 API 返回值一致性
-- 先调 /api/stats/area-distribution，记下广东的 count
-- 再调 /api/stats/province-workers { province: "广东" }，workers.length 应等于上面的 count
```

## 九、边界情况

| 场景 | 预期行为 |
|------|---------|
| 同一人提交了 2 条同日同省日志 | 只计 1 次，projects 合并 |
| 同一人被 3 条不同省份报告列在 workers 中 | 在 3 个省份各计 1 次 |
| 同一人在 A 省提交 + B 省被代填 + C 省出现在 workers | 在 A、B、C 三省各出现 |
| area 为空或 NULL | 跳过 |
| area 不含 `-`（如 GPS 定位） | 跳过 |
| workers 文本中名字无法匹配到用户 | 跳过该名字 |
| 报告状态为 draft | 不纳入统计 |
| 报告类型为 office（公司日报） | 不纳入统计 |
| 用户在 users 表中已软删除 | 出现在统计中（报告已 approved） |
