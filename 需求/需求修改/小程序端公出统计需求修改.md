# 小程序端公出统计 — 区域分布（昨日）问题诊断与修复

> 状态：数据库已清洗，待改代码  
> 日期：2026-06-27

---

## 一、背景

此前区域分布面板存在"面板 2 人、下钻 3 人"的人数不一致问题。经排查，**根因是数据库 area 字段存在大量非标准格式的脏数据**，而非跨省去重逻辑缺陷。

### 业务约束（经确认）

1. **每人单日只能上传一次公出日志**（自己提交或他人代填，二选一）
2. **不会出现同一人多地点的情况**（地点通过选择框填写）
3. 当日被代填后，本人无法再提交

---

## 二、根因：数据库脏数据

### 2.1 脏数据规模

查询 2026年6月+ 的 `daily_reports` 表，共发现 **325 条** area 不含 `-` 的记录，分 32 种模式：

| 脏数据类型 | 示例 | 数量 | 问题 |
|-----------|------|:--:|------|
| 缺省份前缀 | `阳江市平岗镇` | 34 | 缺少"广东省-" |
| 省份简称 | `广东阳江`、`福建莆田` | 48 | "广东" → 应为"广东省" |
| 缺横线 | `安徽省亳州市坛城县` | 26 | 整体无 `-` 分隔 |
| 省名错误 | `新疆省乌鲁木齐市` | 12 | "新疆省" → 应为"新疆维吾尔自治区" |
| 混入公司名 | `陆丰市 明阳叶片厂` | 12 | 含空格和工厂名 |
| 地理错误 | `云南省大理市宾川县` | 22 | 宾川属大理州非大理市 |
| 其他缺横线 | 各种格式 | 171 | 省略了 `-` 分隔符 |

### 2.2 脏数据造成的问题

```
getAreaDistribution 面板:
  addPerson() 中有 if (!area.includes('-')) return;
  → "广东阳江" 无 '-' → 直接丢弃 → 面板少计 1 人

getProvinceWorkers 下钻:
  SQL: WHERE dr.area LIKE '广东-%'
  → "广东阳江" 不以 '广东-' 开头 → 也查不到
  
  BUT: 该 report 的 workers 文本中包含其他人名
  → 其他人名可能通过 path 2/3 被找到
  → 导致该省下钻多出人来
```

**核心矛盾**：脏数据的 area 值既无法被面板识别（无 `-` 直接丢弃），又无法被单省 SQL 精确匹配（`LIKE 'X-%'` 要求 `-` 紧跟前缀），但其中涉及的 workers 文本仍可通过其他路径被部分匹配到，造成两边人数差异。

### 2.3 清洗结果

已于 2026-06-27 完成数据库清洗：

```sql
-- 清洗前
SELECT COUNT(*) FROM daily_reports
WHERE area NOT LIKE '%-%' AND report_date >= '2026-06-01';
-- 结果: 325

-- 清洗后
-- 结果: 0 ✅
```

全部 32 种脏数据已映射为标准"省-市-县"格式（SQL 文件：`backend/sql/clean_area_data_june2026.sql`）。

## 三、剩余代码级改进

数据库清洗后，area 已全部为 `省-市-县` 标准格式。`getAreaDistribution` 和 `getProvinceWorkers` 的核心逻辑无需大改（跨省去重不是问题，因为每人单日只有一条日志）。以下是小幅优化：

### 3.1 前端：清理传参混乱

**现状**：`openProvinceDrill` 传了 `workTypeMonth` 给区域分布无关的 API。

**文件**：`miniapp/src/pages/profile/stats.vue`、`miniapp/src/services/modules/report.js`

```diff
- const res = await reportApi.getProvinceWorkers(p.name, workTypeMonth.value)
+ const res = await reportApi.getProvinceWorkers(p.name)
```

### 3.2 后端：getProvinceWorkers 补充 uidToInfo

**现状**：workers 文本中提到的用户，如果不在该省报告的 user_id 列表中，`uidToInfo` 查不到其信息。

**文件**：`backend/src/core/services/stats.service.js` — `getProvinceWorkers`

改动：workers 文本匹配到的用户名，如果尚未在 `uidToInfo` 中，额外查一次 `users` 表补全。

### 3.3 不做改动

- ❌ 不改变去重 key（`uid` 省内去重已正确）
- ❌ 不合并两个函数（各自逻辑清晰，改动风险大）
- ❌ 不引入日期选择器（固定昨日）
