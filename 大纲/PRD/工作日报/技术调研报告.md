# 技术调研报告：工作日报模块

> 调研日期：2026-08-05
> 调研角色：代码架构师 / 开源情报分析师
> 调研目标：为“工作日报”模块寻找可参考的开源企业后台方案，并重点验证如何做到与现有“公出日志”模块物理隔离、零数据污染。

---

## 1. 结论摘要

1. 推荐 **TeamSpace（Yuusuke9228/groupware）** 作为企业后台工作日报的 Schema 与功能参考。它用 `daily_reports` 及一组 `daily_report_*` 子表完整承载日报业务，不依赖共享 `report_type` 或泛化业务表，且具备模板、草稿、富文本、活动日志、附件、评论、权限、周/月/时间线视图。
2. 推荐 **Repost（zenizh/repost）** 作为 Markdown 编辑与草稿恢复的前端交互参考。它使用 React + Redux + Draft.js，将编辑器原始状态独立存入 `posts.editor_state`，正文 `content` 只保存可检索文本，是“编辑不丢内容、可续写草稿”的好范例。
3. 未筛到完全同时具备“日历拖拽 + Markdown 编辑 + 草稿箱”的单一成熟开源项目。若后续需要这些能力，可组合参考 TeamSpace 的后端 Schema 与 Repost 的前端编辑/草稿设计；按当前确认范围，首期不实现这些复杂交互。
4. 对本项目而言，**不建议继续扩展现有 `daily_reports` 表，也不建议新增 `report_type = 'work_report'`**。推荐使用独立表前缀、独立路由、独立服务目录、独立 Redis key、独立附件目录，并通过独立数据库连接池实现更彻底的数据隔离。

### 1.1 已确认范围（2026-08-05）

经需求对齐，工作日报模块的首期范围收敛为：

- 今日工作总结。
- 明日工作计划。
- 反馈遇到的问题。
- 填报日期、提交人等必要元数据。

首期不实现日历拖拽、Markdown、草稿箱、模板、审批、统计、评论、附件等复杂能力。本报告中的 TeamSpace / Repost 仍作为后续扩展参考，但架构建议按“最小表单 + 独立存储”设计。

## 2. 现有“公出日志”模块边界

调研前已确认当前系统中“公出日志”占用的存储与入口如下：

| 类别 | 现有占用 |
| --- | --- |
| 主表 | `daily_reports` |
| 关联表 | `daily_report_workers` |
| 外部映射 | `wecom_sheet_records`（关联 `daily_report_id`） |
| 视图 | `wps_reports_view` |
| 后端 API | `/api/report/*`、`/api/stats/*` 中与日报/公出统计相关接口 |
| 后端目录 | `backend/src/core/`、`backend/src/features/` 中 report/stats 相关实现 |
| Web 前端 | `webapp/src/views/report/`、`webapp/src/api/report.ts` 等 |
| 小程序 | `miniapp/src/pages/employee/` 等日报填写/统计页面 |

因此，“物理隔离”的验收标准应至少包括：

- 不修改 `daily_reports`、`daily_report_workers`、`wecom_sheet_records` 的结构。
- 不重写 `wps_reports_view`。
- 不新增 `daily_reports.report_type = 'work_report'` 之类的“塞进旧表”方案。
- 新模块不使用 `/api/report/*` 作为唯一入口，也不向旧统计表或旧 Redis key 写数据。

## 4. 推荐案例 1：TeamSpace

### 4.1 项目信息

- 项目名称：TeamSpace
- GitHub：https://github.com/Yuusuke9228/groupware
- 技术栈：PHP 8.1+、MySQL 5.7+、jQuery/Select2/Chart.js
- 说明：自托管企业协作平台，内置日報、日程、任务、工作流、文件管理、Web Database 等功能。

### 4.3 数据独立设计亮点

1. **不依赖 `report_type` 泛化**：TeamSpace 没有把日程、任务、出差、日报混进同一张大表，而是每个业务域独立建表。日报扩展只发生在 `daily_report_*` 系列表内。
2. **主表 + 子表聚合**：正文、标签、评论、点赞、附件、权限、活动日志分别独立建模，删除主表时通过 `ON DELETE CASCADE` 清理子表，不需要应用层手工拼接字符串。
3. **跨模块关联只走关系表**：日报需要关联日程或任务时，使用 `daily_report_schedules`、`daily_report_tasks` 显式关系表，而不是在 `content` 中存 ID 或把业务字段写进 `daily_reports`。
4. **结构化内容独立保存**：`detail_json`、`daily_report_template_sections`、`daily_report_activity_logs` 将模板项和活动明细从普通正文中拆出，便于统计、校验和后续扩展。

### 4.4 前端交互亮点

参考文件：

- `public/js/daily-report.js`
- `views/daily_report/form.php`
- `views/daily_report/week.php`
- `views/daily_report/month.php`
- `views/daily_report/timeline.php`

主要亮点：

1. **草稿箱**：表单中有“下書きとして保存する（保存为草稿）”复选框，提交时把 `status` 置为 `draft`；列表和详情能区分草稿与已发布日报。
2. **富文本编辑**：正文使用 `contenteditable` 富文本编辑器，提交前通过 `syncEditorToField()` 将编辑器 HTML 同步到隐藏字段，并保存 `content_format='html'`。
3. **模板化结构化输入**：选择模板后，表单按 `template_sections` 渲染动态字段；支持文本、多行文本、checklist、number、rating、toggle 等输入类型。
4. **动态明细行**：活动日志、分析明细分录都支持前端动态增删行，并统一收集为 JSON 提交。
5. **日历化浏览**：周视图以星期卡片展示每日日报；月视图按日期格子展示日报数量和“创建”入口，点击数量进入当日时间线。
6. **完整工作流**：详情页支持点赞、评论、附件、标签、权限范围、关联日程/任务，形成“填写、归档、检索、协同”闭环。

需要说明的是，TeamSpace 的日历是“日期网格 + 创建/计数入口”，并未实现日报卡片在日历上的拖拽排期。日历拖拽可作为我们自己的增强点，不必从该项目照搬。

## 5. 推荐案例 2：Repost

### 5.1 项目信息

- 项目名称：Repost
- GitHub：https://github.com/zenizh/repost
- 技术栈：Ruby on Rails + PostgreSQL + React + Redux + Draft.js + remark/Markdown
- 说明：面向团队日报交流的开源应用，README 明确标注为 pre-alpha，适合学习交互与 Schema，不适合直接生产依赖。

### 5.2 核心数据表结构摘要

参考 `db/schema.rb`：

| 表名 | 核心字段 | 职责 |
| --- | --- | --- |
| `posts` | `user_id`、`content`、`editor_state`、`reactions_count` | 日报帖子；`content` 为纯文本，`editor_state` 为 Draft.js 原始 JSON |
| `comments` | `post_id`、`user_id`、`content` | 评论 |
| `reactions` | `post_id`、`user_id`、`name` | 表情反应 |
| `stars` | `post_id`、`user_id` | 收藏/星标 |
| `templates` | `user_id`、`name`、`content` | 用户日报模板 |
| `channels` | `name` | 频道 |
| `subscriptions` | `channel_id`、`user_id` | 用户订阅关系 |
| `services` | `type`、`webhook_url`、`channel`、`on_post`、`on_comment` | Slack 等外部通知 |

### 5.3 数据独立设计亮点

1. **正文与编辑状态分离**：`posts.content` 保存可检索的纯文本；`posts.editor_state` 保存 Draft.js `convertToRaw` 结果。这样既支持 Markdown 预览/检索，也支持恢复编辑器状态。
2. **互动数据独立建模**：评论、反应、星标分别建表，避免把列表塞进 `posts` 的 JSON 字段，也方便按模块拆分。
3. **模板独立于帖子**：`templates` 表不依赖具体日报，用户可维护自己的模板集合。
4. **频道/订阅独立**：可见性通过 `channels` + `subscriptions` 关系表表达，不污染日报正文。
5. **外部服务独立**：Slack Webhook 等配置放在 `services` 表，与日报业务解耦。

### 5.4 前端交互亮点

参考文件：

- `app/javascript/components/PostEditor.jsx`
- `app/javascript/components/PostForm.jsx`
- `app/javascript/components/PostPreview.jsx`
- `app/javascript/components/Markdown.jsx`
- `app/javascript/actions/editorActions.js`
- `app/javascript/actions/postActions.js`

主要亮点：

1. **Redux 保存编辑器状态**：`PostEditor` 每次 `onChange` 都调用 `setEditorState(editorState)`，编辑器状态常驻 Redux，不依赖组件内部临时变量。
2. **Markdown 实时预览**：`PostPreview` 从 Draft.js ContentState 取纯文本，交给 remark 渲染 Markdown，实现“编辑/预览”双栏体验。
3. **草稿续写能力**：创建和更新帖子时，前端用 `convertToRaw(content)` 序列化 Draft.js 状态，提交 `editorState`；后端持久化后，再次编辑可恢复原始编辑器状态。
4. **Redux + axios middleware**：帖子创建/更新走统一 action，前端可清晰追踪保存状态、失败重试和后续跳转。

## 6. 案例共性：模块解耦最佳实践

从两个推荐案例及其他候选项目中可提炼以下共性：

### 6.1 表设计层面

- 每个业务模块拥有自己的主表和子表，不通过大而全的通用表承载所有业务。
- 模块内互动数据（评论、点赞、标签、附件、权限）拆成独立子表，按主表 `id` 关联。
- 跨模块引用优先使用“关系表”，避免在主表正文里存外部 ID 或使用多态字段。
- 用 `status` 枚举表达草稿/发布等生命周期，而不是靠删除记录或复杂状态字段隐式表达。
- 编辑器原始状态与最终可展示内容分开保存，兼顾检索和编辑体验。

### 6.2 服务/API 层面

- 独立路由前缀、独立 Service、独立 Repository，避免旧模块继续膨胀。
- 新模块只通过认证/用户 ID 读取共享基础数据，不直接修改旧模块表。
- 事务边界限定在新模块表内；如需跨模块读用户信息，使用只读查询或专用视图。

### 6.3 前端层面

- 独立页面路由与独立 API 封装文件。
- 编辑器状态放进全局状态或本地持久化，避免切页丢失。
- 日历、列表、时间线、草稿箱作为不同视图共用同一套 API，不散落业务逻辑。

## 7. 针对“物理隔离”的初步架构建议

### 7.1 隔离强度分级

| 级别 | 方案 | 适用性 |
| --- | --- | --- |
| T1 | 独立 MySQL 实例，数据库、账号、备份完全独立 | 隔离最强，但运维与跨库读取成本最高 |
| T2 | 同实例独立数据库/Schema + 独立 DB 账号 + 独立连接池 | 推荐：数据层隔离明确，仍可低成本读取 `users` 等基础数据 |
| T3 | 同一数据库，仅独立表前缀 | 不推荐作为“物理隔离”最终方案，权限与备份无法彻底分开 |

建议本项目按 **T2** 落地：新建独立数据库或独立 Schema，例如 `wx_app_oa_work_report`，并新增 `workReportPool` 专用连接池。这样可以做到表、账号、备份、索引互不干扰，同时保留对 `users` 的只读引用能力。

### 7.2 后端目录与路由

```text
backend/src/features/work-report/
  routes/work-report.routes.js
  controllers/work-report.controller.js
  services/work-report.service.js
  repositories/work-report.repository.js
  validators/work-report.validator.js
```

路由建议：

- 员工端：`/api/work-report/daily/*`
- 管理端：`/api/work-report/admin/*`
- 文件上传：独立于旧附件逻辑，走 `/api/work-report/files/*`

禁止改动：

- `backend/src/core/controllers/report.controller.js`
- `backend/src/core/services/report.service.js`
- 旧 `stats` 相关接口

### 7.3 数据表草案

以下表名统一使用 `work_report_` 前缀，不使用 `daily_reports`，也不新增 `report_type` 值。

```sql
-- 主表：工作日报
CREATE TABLE work_report_daily (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  user_id INT UNSIGNED NOT NULL COMMENT '只读引用 users.id',
  report_date DATE NOT NULL,

  content MEDIUMTEXT NOT NULL,
  content_format ENUM('markdown','html','text') NOT NULL DEFAULT 'markdown',
  editor_state LONGTEXT NULL COMMENT 'Markdown/富文本编辑器原始状态，用于续写',
  status ENUM('draft','published','archived') NOT NULL DEFAULT 'draft',
  template_id BIGINT UNSIGNED NULL,
  visibility ENUM('private','department','company') NOT NULL DEFAULT 'private',
  submitted_at DATETIME NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  deleted_at DATETIME NULL,
  INDEX idx_wrd_user_date (user_id, report_date),
  INDEX idx_wrd_status_date (status, report_date)

-- 模板与结构化项目
CREATE TABLE work_report_template (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  name VARCHAR(120) NOT NULL,
  content MEDIUMTEXT NULL,

CREATE TABLE work_report_template_section (

CREATE TABLE work_report_comment (
```

### 7.3.1 按当前最小范围收敛后的核心表

按照“只填写今日工作总结、明日工作计划、反馈遇到的问题”的已确认范围，首期只需要一张主表，不需要模板、评论、点赞、附件等子表：

```sql
CREATE TABLE work_report_daily (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  user_id INT UNSIGNED NOT NULL COMMENT '填报人，只读引用 users.id',
  report_date DATE NOT NULL COMMENT '工作日报日期',
  today_summary TEXT NULL COMMENT '今日工作总结',
  tomorrow_plan TEXT NULL COMMENT '明日工作计划',
  issues TEXT NULL COMMENT '反馈遇到的问题',
  status ENUM('draft','submitted') NOT NULL DEFAULT 'draft' COMMENT '草稿/已提交',
  submitted_at DATETIME NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  deleted_at DATETIME NULL,
  UNIQUE KEY uk_wrd_user_date (user_id, report_date),
  INDEX idx_wrd_date (report_date)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='工作日报主表';
```

如果后续确需 Markdown、草稿箱或日历拖拽，再以 `work_report_*` 前缀新增子表或扩展字段，不影响首期范围。

后续可扩展：

- `work_report_tag`、`work_report_tag_relation`
- `work_report_reaction`
- `work_report_mention`
- `work_report_activity_log`
- `work_report_calendar_entry`（用于日历排期和拖拽更新）
- `work_report_reminder`

### 7.4 前端隔离

- Web 管理端：新增 `/work-report/*` 路由，API 文件放 `webapp/src/api/workReport.ts`，页面放 `webapp/src/views/work-report/`。
- 小程序端：页面放 `miniapp/src/pages/employee/work-report/`，服务封装放 `miniapp/src/services/modules/workReport.ts`。
- 状态管理使用独立 store，不写入现有 `report` 或 `stats` store。
- 通用组件可复用，但业务组件不得读取旧 `daily_reports` 的 DTO。

### 7.5 存储与缓存隔离

- 附件目录：`uploads/work-report/`，禁止写旧 `uploads/report/` 等目录。
- Redis key：统一 `work-report:*` 前缀，禁止使用 `report:*`、`stats:*`。
- 导出文件：`exports/work-report/`。
- 定时任务：独立 `work-report-*` 任务，不复用旧报表任务。

### 7.6 迁移与验收清单

实施前先做“隔离红线”检查：

1. `rg "daily_reports" backend/src/features/work-report miniapp/src/pages/employee/work-report webapp/src/views/work-report` 应只出现在只读 `users` 相关说明或测试夹具中，不出现业务读写。
2. 新 SQL 文件只建 `work_report_*` 表，不改任何旧表。
3. `SHOW CREATE TABLE work_report_daily` 中无旧表外键；跨库读取用户信息时通过独立连接池的只读查询。
4. `/api/report/*`、`/api/stats/*` 的请求日志中，新模块请求数量应为 0。
5. 旧 `wps_reports_view` 查询结果在迁移前后完全一致。
6. 备份、恢复、回滚演练只包含 `work_report_*` 表，不影响旧库。

## 8. 后续建议

1. 下一阶段生成正式 PRD 与数据设计时，以“今日总结 / 明日计划 / 遇到的问题”三个字段为最小交付，不引入额外业务能力。
2. 数据层继续坚持 `work_report_*` 独立表、独立连接池、独立路由和独立前端模块，不触碰现有公出日志相关表。
3. 前端首期采用普通多行文本框即可；Markdown、草稿箱、日历拖拽、模板等保留为后续扩展项，不进入首期范围。
4. 调研项目仅供架构借鉴，不建议直接引入 TeamSpace 或 Repost 作为代码依赖，尤其注意许可证与 pre-alpha 风险。
