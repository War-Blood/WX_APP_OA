## 执行摘要

本轮对 OA 公出日志系统进行了一次全面的架构审计和性能诊断，覆盖 **前端（Vue3 管理后台 + uni-app 小程序）、后端（Node.js/Express）、数据库（MySQL）和基础设施（Docker/PM2/Nginx）** 四个层面，共发现 **35 项问题**，经测试团队定向验证确认全部属实。

**核心结论**：系统架构基础扎实，安全基础设施较好，但存在严重的**数据库索引缺失**、**认证热路径瓶颈**、**前后端代码零共享**三大系统性缺陷。当前数据量小（<100条日报）未暴露性能问题，但架构缺陷会随数据增长迅速恶化。

## 第一部分：P0 阻塞级问题（立即修复）

### P0-1：daily_reports 表严重缺乏索引 🔴

**发现者**：速飞驰 | **验证者**：严过关 | **确认状态**：✅ 已确认

**问题**：核心查询 `report.service.js:152` 的 WHERE 条件（user_id / status / report_date / keyword）无任何覆盖索引，每次都是全表扫描 + filesort。

```sql
-- 当前执行：全表扫描 + Using filesort
SELECT dr.*, u.nickname AS userName, u.department
FROM daily_reports dr LEFT JOIN users u ON dr.user_id = u.id
WHERE [动态条件] ORDER BY dr.created_at DESC LIMIT ? OFFSET ?
```

**实测数据**：当前 38ms（仅因数据量 < 100 条），万级数据下预计飙升至 500ms+。

**修复方案**：

```sql
-- 核心索引（覆盖 80% 查询场景）
ALTER TABLE daily_reports ADD INDEX idx_user_date_status (user_id, report_date, status, deleted_at);

-- 统计/管理查询
ALTER TABLE daily_reports ADD INDEX idx_date_status_type (report_date, status, report_type, deleted_at);

-- 排序优化
ALTER TABLE daily_reports ADD INDEX idx_created_at (created_at);

-- 相关方全文索引
ALTER TABLE daily_reports ADD FULLTEXT INDEX ft_workers (workers);
ALTER TABLE daily_reports ADD INDEX idx_related_party (related_party);
```

**预期收益**：响应时间 ↓60-80%

### P0-2：认证中间件每次请求都查 DB 🔴

**发现者**：速飞驰 | **验证者**：严过关 | **确认状态**：✅ 已确认

**位置**：`backend/src/common/middleware/auth.js:35-38`

```js
const rows = await db.query(
  'SELECT status, role FROM users WHERE id = ? AND deleted_at IS NULL',
  [decoded.userId]
);
```

JWT 已验证签名和过期，仍对每个请求执行一次 DB 查询。10 次连续请求均耗时 31-48ms 无差异（无缓存预热现象，每次都是同等开销）。

**修复方案**：增加 Redis 缓存层（TTL 5 分钟），缓存未命中时降级到 DB。

```js
const cacheKey = `user:status:${decoded.userId}`;
let userStatus = await redis.get(cacheKey);
if (!userStatus) {
  const rows = await db.query('SELECT status, role FROM users WHERE id = ? AND deleted_at IS NULL', [decoded.userId]);
  userStatus = { status: rows[0].status, role: rows[0].role };
  await redis.setEx(cacheKey, 300, JSON.stringify(userStatus));
}
req.user = { ...decoded, role: userStatus.role };
```

**预期收益**：认证延迟 ↓70%（10-30ms → ~1ms），DB 查询减少 99%

### P0-3：getWorkerStats 全表扫描 + 应用层聚合 🔴

**发现者**：速飞驰 | **验证者**：严过关 | **确认状态**：✅ 已确认

**位置**：`backend/src/core/services/report.service.js:914-938`

```js
// 无 LIMIT，读取全部 approved 记录
const rawRows = await db.query(
  "SELECT workers, report_date FROM daily_reports WHERE workers IS NOT NULL AND workers != '' AND status = 'approved'"
);
// JavaScript 逐条 split + 聚合
for (const row of rawRows) {
  const names = row.workers.split(/[、,，\s\/\n]+/);
  // ... 构建 personMap ...
}
```

**实测数据**：当前 144ms（66条记录），万级数据预计 500ms-2000ms。

**修复方案**：使用 `daily_report_workers` 关联表 + SQL GROUP BY 聚合。

```sql
SELECT u.id, u.nickname AS name, COUNT(DISTINCT drw.report_id) AS total,
  COUNT(DISTINCT CASE WHEN MONTH(dr.report_date) = MONTH(CURDATE()) THEN drw.report_id END) AS monthCount,
  MAX(dr.report_date) AS lastDate
FROM daily_report_workers drw
JOIN daily_reports dr ON drw.report_id = dr.id
JOIN users u ON drw.worker_uid = u.id
WHERE dr.status = 'approved'
GROUP BY u.id, u.nickname ORDER BY total DESC
```

**预期收益**：响应时间 ↓90%

### P0-6：前后端零代码共享 🔴

**发现者**：寇界明 | **验证者**：严过关（测试 G 确认接口不一致）

webapp（TypeScript）和 miniapp（JavaScript）的 API 类型定义、业务逻辑、工具函数完全独立维护。严过关的 API 对比测试进一步发现小程序缺失 `workerStats`、回收站、企业微信导出等多个接口。

**修复**：抽取 `shared/` 包，至少共享 API 类型定义、路径常量和纯函数工具。

## 第七部分：架构评价总览

### 各项评分

| 维度 | 评分 | 说明 |
|------|------|------|
| 安全基础设施 | ⭐⭐⭐⭐ | RBAC + bcrypt + 限流 + SQL 注入防护均到位，P0 问题集中在配置层面 |
| 代码分层 | ⭐⭐⭐⭐ | 清晰的三层架构（Routes→Controllers→Services），features 扩展设计合理 |
| 错误处理 | ⭐⭐⭐ | 错误码体系完善但 HTTP 状态码统一返回 200 |
| 数据库设计 | ⭐⭐⭐ | RBAC 设计优秀，但核心表缺索引 + workers 字段需废弃 |
| 前端架构 | ⭐⭐⭐ | Composition API + Pinia 方案现代，但巨型组件 + 零代码共享拖后腿 |
| 类型安全 | ⭐⭐ | webapp 严格 TypeScript，miniapp 完全无类型 |
| 可扩展性 | ⭐⭐⭐ | 新功能接入路径清晰，但无集群、无 API 版本化 |
| 运维可靠性 | ⭐⭐⭐ | Docker + PM2 + 健康检查，但单实例无冗余 |
| 缓存利用率 | ⭐ | Redis 已连接但无任何业务缓存，严重浪费 |

### 架构优点（保持）

1. **安全基础设施扎实**：RBAC 三级权限、bcrypt 密码哈希、TOTP 二次验证、SQL 注入防护
2. **分层架构设计合理**：Routes → Controllers → Services，新模块按 features 目录组织
3. **规范化程度高**：统一响应格式、60+ 错误码、Joi 参数校验、JSDoc 注释
4. **部署方案完整**：Docker Compose 一键部署、PM2 进程管理、健康检查
5. **前端 API 层封装优秀**：Token 自动续期（防并发）、统一错误处理、TypeScript 严格模式

### 核心架构风险

1. **数据库索引缺失** — 当前小数据量掩盖了问题，数据增长后性能会断崖式下降
2. **无缓存策略** — Redis 闲置，所有读压力直打 MySQL，认证热路径尤为突出
3. **单点瓶颈** — PM2 单实例 fork 模式，无法扩容，大导出任务可能 256MB OOM
4. **代码一致性风险** — 两套平行目录 + 前后端零共享，修改一处可能忘记同步另一处
