# 公出统计优化 — 设计回应

> 针对你的 3 条需求,站在实用角度给出设计思路。先诊断现状,再逐条给方案。

---

## 一、先说你关心的:"公出统计模块存在什么问题"

我通读了小程序 `stats.vue`、Web 后台 `report/*.vue`、后端 `stats.service.js`,发现以下**实质性问题**:

| # | 问题 | 严重度 | 位置 | 说明 |
|:--:|------|:--:|------|------|
| P1 | **日历数字误导** | 🔴 | 小程序 `calendar` tab / Web `calendar.vue` | 现在日历格显示的是**当天"已审核通过的日报条数"**(提交人次),不是人头数。同一个人当天被代填+自己提交会重复计数,且显示 0 不等于"无人提交"。**管理员容易看错** |
| P2 | **缺失人数缺上下文** | 🟡 | 小程序 `daily` tab / Web `daily-status.vue` | 摘要条只给"已提交 N / 缺失 N",但**没告诉 N 是基于多少人算的**。比如"缺失 3"是 10 人里缺 3,还是 50 人里缺 3?决策完全不同 |
| P3 | **工作类型分布无汇总维度** | 🟡 | 小程序 `workers` tab / Web `work-type.vue` | 表格只有"每人一行",没有"全公司这个月每种类型多少天"的总览,也没有补录次数。想快速回答"这个月待工/请假严重吗"要自己加 |
| P4 | **"人员分布"入口混乱** | 🟡 | 小程序 `workers` tab | 同一 Tab 里塞了"工作类型分布"+"区域分布(昨日)"两件事,标题却叫"人员分布",导航语义不清 |
| P5 | **小程序非管理员看不到统计** | 🟢 | 小程序 `stats.vue:6` | `v-if="userStore.isAdmin"` 把 4 个统计 Tab 都藏了,普通员工只能用"个人统计"。如果你希望员工也能看到全员状态,需要放开 |

**结论**:核心数据都对,问题是**展示方式让决策者看不到"全貌"**——缺少"基数(总共多少人)"和"汇总(合计)"两个维度。

## 二、三个需求的设计方案

### 需求 a:全员当日 — 今日/明日切换

**目标**:默认看今日,切到明日看"所有人员的明日计划工作状态",按工作状态分组。

**交互设计**:

```
┌──────────────────────────────────────────┐
│ 公出统计                                  │
├──────────────────────────────────────────┤
│ ‹ [昨日 2026-08-03 ▾] ›   [今日][明日]    │  ← 日期条右侧加今日/明日 segment
│ ┌────────┐ ┌────────┐                    │
│ │ 已提交 │ │ 缺失   │                    │
│ │  32   │ │  8     │                    │
│ └────────┘ └────────┘                    │
│  共 40 人 · 已提交 32 · 缺失 8           │  ← 加上基数,回答"基于多少人"
│──────────────────────────────────────────│
│ 未提交 (8)  ▍ 补公出 (3)  ▍ 请假 (2)      │
│ [每人一张卡:姓名/项目/区域]                 │  ← 不显示工号
└──────────────────────────────────────────┘
```

**设计要点**:
1. **segment 放日期条右侧**:沿用现有日期条布局 `‹ [昨日 2026-08-03 ▾] ›`,在右箭头右侧并列加两个选项"今日 / 明日",当前值高亮。切到"明日"时日期条显示"明日 2026-08-04",切回"今日"显示"今日 2026-08-03"。
2. **加一行基数提示**:"共 N 人 · 已提交 X · 缺失 Y",让缺失数字有上下文。
3. **明日视图**:切到明日时,日期条显示"明日 2026-08-04";数据来源 = 员工昨天/今天填写的**明日工作类型**(`tomorrow_work_type` 字段已有)。分组改为:
   - **未填写明日计划**(没填 tomorrow_work_type 的)——重点提示
   - **计划公出/外场**(tomorrow_work_type = 工作(陆)/工作(海))
   - **计划待工/在途**
   - **计划请假**
   - 这样即使明日未到,也能看"明天谁预计在外、谁没排计划"。
4. 明日数据**后端新增一个接口**(`getTomorrowStatus`),按 `tomorrow_work_type` 分组返回,与今日 `getDailyStatus` 结构对称。

### 需求 b:日历 — 已提交/未提交

**目标**:日历格数字从"提交人数"改为"已提交 / 未提交";全员提交 → 淡绿背景,否则白底。

**交互设计**:

```
     2026年8月            [‹][8月][›]
 ┌───────────────────────────────────────┐
 │ 图例:  ● 全员提交 ● 部分缺失 ● 无数据  │
 ├───────────────────────────────────────┤
 │  一  二  三  四  五  六  日             │
 │              1     2     3     4      │
 │           32/40  40/40 20/40  8/40   │  ← 每格: 已提交/总人数
 │               绿    白    白           │
 │  5     6     7     8   ...            │
 │ 12/40  28/40 40/40 40/40              │
 └───────────────────────────────────────┘
```

**设计要点**:
1. **每格数字改为 `已提交/总人数`**(如 `32/40`),一眼看出缺口。
2. **背景规则**:
   - 全部提交 → 淡绿 `#E8F5E9`(满足你的要求)
   - 部分提交 → 白色(满足你的要求)
   - 无数据(当月没到/休假日)→ 浅灰,不误导
3. **点击某天 → 下钻当日明细**(复用 daily-status 的视图):当天谁提交了、谁缺失。
4. **后端扩展 `getDailyCounts`**:现在只返回 `{date, count}`,需扩展为 `{date, submitted, total}`。total = 当天在职人数(`worker_status='active'` 的作业人员),submitted = 当天去重后已提交人数(复用 `getAllStats` 里现成的缺失计算逻辑,取反即可)。

### 需求 c:工作类型分布 — 月份切换 + 汇总行 + 补录次数

**目标**:右上角月份切换;表格第一行加汇总(所有人员各状态总天数);左侧加"补"列(补录次数)。

**交互设计**:

```
┌──────────────────────────────────────────────┐
│ 工作类型分布                        [‹][8月][›] │
├──────────────────────────────────────────────┤
│ 姓名  补  陆  海  待  途  假  计             │ ← 加"补"列,不显示工号
│──────────────────────────────────────────────│
│ 汇总  12  98 45 23 15  8 189  ⏫ 加粗         │ ← 第一行汇总
│ 张三   2  22  3  0  0  1  26                  │
│ 李四   0  15  8  1  0  2  26                  │
│ 王五   1   8  5  2  0  0  15                  │
└──────────────────────────────────────────────┘
```

**设计要点**:
1. **月份切换**:右上角左右箭头 + 当前月份(小程序里 `workers` tab 目前没有,Web 有——补上小程序端即可)。
2. **汇总行置顶加粗**:每列合计(全公司该类型总天数),名称用"汇总"。
3. **"补"列**:统计该人员当月 `report_type='biz_trip_supplement'` 的去重天数(补录次数)。后端 `getWorkerWorkTypes` 需加这个字段;补录天不应重复计入各工作类型(保持现有"同天防双计"逻辑)。
4. **排序**:默认按"计"(总天数)降序,把活跃度最高的人排前面;汇总行始终置顶。

## 四、后端数据能力清单(需新增/扩展)

| 功能 | 后端改动 | 现状态 |
|------|---------|:--:|
| 今日/明日切换 | 新增 `getTomorrowStatus(date)` — 按 `tomorrow_work_type` 分组所有在职人员 | 缺失 |
| 日历已提交/未提交 | 扩展 `getDailyCounts` → 返回 `{date, submitted, total}` | 需扩展 |
| 工作类型汇总行 | 前端可自算(数据完整),无需后端 | 可前端做 |
| 补录次数 | 扩展 `getWorkerWorkTypes` → 每人加 `supplementCount` | 需扩展 |

**API 改动汇总**(全部沿用 POST + JSON 约定):
- `POST /api/report/tomorrow-status`(新)
- `POST /api/stats/daily-counts`(改:返回 submitted/total)
- `POST /api/stats/worker-work-types`(改:返回 supplementCount)

## 五、建议实施顺序

1. **先做日历**(需求 b)——后端扩展小、视觉效果直观、解决 P1 误导问题。
2. **再做工作类型分布**(需求 c)——纯前端居多(汇总行),补录次数加一个后端字段。
3. **最后做今日/明日**(需求 a)——需要新接口 + 双端同步,工作量最大。
