### BUG-01 🔴 P0 — 请假类型映射 swap，三页面映射不一致

**发现位置**：
- `miniapp/src/pages/attendance/leave-apply/index.vue` 第 49 行
- `miniapp/src/pages/attendance/leave-detail/index.vue` 第 46 行
- `miniapp/src/pages/attendance/leave-list/index.vue` 第 52 行

**问题描述**：

三处 leaveType 映射定义相互矛盾：

| 页面 | 映射定义 | 正确性 |
|------|------|:--:|
| leave-apply (line 49) | `'事假': 'sick', '病假': 'personal'` | ❌ 中文↔英文交换 |
| leave-detail (line 46) | `sick: '事假', personal: '病假'` | ❌ 与 leave-apply 一致但语义错误 |
| leave-list (line 52) | `sick: '病假', personal: '事假'` | ✅ 正确 |

**复现步骤**：
1. 用户在小程序选择「事假」提交请假
2. leave-apply 发送 `leaveSubtype: "sick"` 到后端（应为 "personal"）
3. 后端存入数据库 `leave_subtype = "sick"`
4. 在「考勤中心」列表页 (leave-list) 查看 → 显示「病假」（因为 leave-list 正确映射 sick→病假）
5. 点击进入详情页 (leave-detail) → 显示「事假」（因为 leave-detail 错误映射 sick→事假）

**实际结果**：用户在列表页看到「病假」，点进去变成「事假」，前后矛盾。且底层存储的是 `sick`（病假），而非用户实际意图的 `personal`（事假）。

**预期结果**：全链路统一：事假↔personal，病假↔sick。

**修复建议**：
- leave-apply: 将 `'事假': 'sick'` 改为 `'事假': 'personal'`，`'病假': 'personal'` 改为 `'病假': 'sick'`
- leave-detail: 将 `sick: '事假'` 改为 `sick: '病假'`，`personal: '病假'` 改为 `personal: '事假'`
- leave-list: 保持不动（已正确）
- **需评估历史数据迁移**：数据库中已存在 sick/personal 互相交换的历史记录

### BUG-02 🔴 P0 — my-schedule 调用管理员端点，普通员工 403

**发现位置**：
- `miniapp/src/pages/attendance/my-schedule/index.vue` 第 112 行
- `miniapp/src/services/modules/attendance.js` 第 5 行
- `backend/src/features/attendance/routes/attendance.routes.js` 第 12 行

**问题描述**：

`my-schedule` 页面调用 `attendanceApi.getScheduleList()`，该方法请求的是 `/api/attendance/schedule/list`（管理员端点，需要 admin/superadmin 角色）。但该页面已定义专用的 `getMySchedule()` 方法（第 6 行，调用 `/api/attendance/schedule/my-schedule`），却未被使用。

**路由定义**：
```js
// line 12: 管理员端点
router.post('/schedule/list', authenticate, requireRole('admin', 'superadmin'), ...)
// line 20: 全员端点
router.post('/schedule/my-schedule', authenticate, ...)
```

**复现步骤**：
1. 以普通员工身份登录小程序
2. 进入「我的排班」页面
3. 后端返回 403 Forbidden

**实际结果**：普通员工无法查看排班。

**预期结果**：所有用户可查看自己的排班。

**修复建议**：
- `my-schedule/index.vue` 第 112 行：将 `attendanceApi.getScheduleList(...)` 改为 `attendanceApi.getMySchedule(...)`
- 注意：`getMySchedule` 返回格式不同于 `getScheduleList`，需同步调整数据解析逻辑（`res.data?.list` → `res.data`）

### BUG-10 🔴 P0 — leave/detail 始终返回"申请单不存在"

**发现位置**：`backend/src/features/attendance/services/leave.service.js` 第 49-52 行

**问题描述**：

`db.query()` 内部已对 mysql2 的 `[rows, fields]` 做了一层解构，直接返回 `rows` 数组。但 `detail()` 函数中错误地再次解构：

```js
// database.js: 已解构 → 返回 rows 数组
async function query(sql, params = []) {
  const [rows] = await oaPool.query(sql, params);  // 第一层解构
  return rows;  // 返回数组
}

// leave.service.js detail(): 错误地二次解构
const [rows] = await db.query(...);  // 二次解构 → rows 变成第一个 row 对象！
if (!rows.length) throw ...;         // row 对象无 .length → undefined → 始终抛异常
```

而同一文件中 `cancel()`、`myList()` 等函数均正确使用了 `const rows = await db.query(...)`。

**复现步骤**：调用任意 `/api/attendance/leave/detail` → 始终返回 `code=2802 "申请单不存在"`

**实际结果**：✅ API 实测确认，任意 requestId 均返回 2802

**修复建议**：将 `const [rows] = await db.query(...)` 改为 `const rows = await db.query(...)`

### BUG-04 🟡 P1 — leaveSubtype 后端无白名单校验

**发现位置**：`backend/src/features/attendance/services/leave.service.js` 第 27-61 行

**问题描述**：

`apply()` 和 `updateRequest()` 函数仅校验 `leaveSubtype` 是否非空，未校验其值是否在合法集合内。攻击者或前端 BUG 可导致任意字符串写入 `leave_subtype` 字段。

**复现步骤**：
1. 调用 `/api/attendance/leave/apply`，传入 `leaveSubtype: "invalid_type_xyz"`
2. 后端接受并写入数据库

**实际结果**：数据库出现脏数据，前端无法正确展示。

**预期结果**：后端校验 leaveSubtype ∈ {annual, sick, personal, marriage, funeral, other}，不合法时返回 400。

**修复建议**：
```js
const VALID_LEAVE_SUBTYPES = ['annual', 'sick', 'personal', 'marriage', 'funeral', 'other'];
if (!VALID_LEAVE_SUBTYPES.includes(leaveSubtype)) {
  throw new ValidationError('无效的请假类型');
}
```

### BUG-05 🟡 P1 — 多处 `new Date()` 使用时区依赖本地环境

**发现位置**：
- `backend/src/features/attendance/services/schedule.service.js` 第 56、58、163、167 行
- `backend/src/features/attendance/services/trip.service.js` 第 72、75-76 行
- `backend/src/features/attendance/services/summary.service.js` 第 54、122、344 行

**问题描述**：

服务端多处使用 `new Date(dateString)` 解析日期字符串，行为依赖服务器本地时区。若服务器 UTC 时区与业务时区（北京时间 UTC+8）不一致，日期计算将偏移一天。

**风险场景**：
- 用户提交 `startDate: "2026-07-06"`，服务器 UTC 时间解析为 `2026-07-06T00:00:00.000Z`
- 但在 UTC-5 时区服务器上，`new Date("2026-07-06")` 可能解析为 `2026-07-05T19:00:00.000Z`，导致日期差一天

**修复建议**：统一使用 `new Date(dateString + 'T00:00:00+08:00')` 或引入 dayjs 时区插件。

### BUG-06 🟢 P2 — 出差开始无并发锁

**发现位置**：`backend/src/features/attendance/services/trip.service.js` 第 28-51 行

**问题描述**：

`startTrip()` 先查询是否有进行中的出差（SELECT），再插入新记录（INSERT）。在高并发场景下（如用户快速双击），两个请求可能同时通过 SELECT 检查，导致创建两个进行中的出差。

```js
// 检查是否有进行中的出差 (非原子)
const active = await db.query(...);
if (active.length > 0) throw ...
// 插入 (两个请求可能同时到达这里)
const result = await db.execute('INSERT...');
```

**复现步骤**：用户快速点击两次「开始出差」按钮。

**修复建议**：添加数据库唯一约束 `UNIQUE(applicant_id, status)` 其中 status='in_progress'，或使用 MySQL `GET_LOCK()`。

for (const user of users) {

### BUG-11 🟡 P1 — Web 排班日历每日状态不显示（scheduleDate 格式不匹配）

**发现位置**：`webapp/src/views/attendance/Schedule.vue` 第 185-187 行

**问题描述**：后端返回 `scheduleDate` 为 ISO 时间戳 `"2026-06-30T16:00:00.000Z"`，但 Element Plus 日历的 `data.day` 为 `"2026-07-01"` 格式。前端直接用作 key → `daySummary` 永远查不到 → 日历空白。

**复现步骤**：Web 后台打开「排班日历」→ 日历格无状态标签/无背景色

**根因链路**：
```
MySQL DATE '2026-07-01' → mysql2→JS Date → JSON→"2026-06-30T16:00:00.000Z"
                                                                  ≠
                                                      日历 data.day "2026-07-01"
```

**修复**：第 185 行 `s.scheduleDate` 后加 `.slice(0, 10)` 截取日期部分
