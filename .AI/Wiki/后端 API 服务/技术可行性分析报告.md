## 1. 技术栈可行性评估

### 1.1 技术选型总览

| 层面 | 选型 | 版本要求 | 可行性 | 说明 |
|------|------|----------|--------|------|
| 运行时 | Node.js | 18.x LTS | ✅ 可行 | 服务器已确认安装，LTS 版本长期支持 |
| Web 框架 | Express | 4.x | ✅ 可行 | npm 包已配置，生态成熟，社区活跃 |
| 数据库 | MySQL | 8.0 | ✅ 可行 | 服务器 MySQL 8.0 已运行，需新建 `wx_app_oa` 库 |
| 缓存 | Redis | 6.x+ | ✅ 可行 | 需安装部署（详见第 4 节） |
| 认证 | JWT (jsonwebtoken) | ^9.0.2 | ✅ 可行 | 标准 Bearer Token 方案 |
| 参数校验 | Joi | ^17.11.0 | ✅ 可行 | 声明式校验，学习成本低 |
| 日志 | Winston | ^3.11.0 | ✅ 可行 | 支持多传输通道、分级日志 |
| 安全 | Helmet + CORS | - | ✅ 可行 | Express 标准中间件 |
| API 文档 | Swagger | - | ✅ 可行 | JSDoc 注释自动生成 |

### 1.2 Express + MySQL + Redis 组合评估

**优势：**
- **轻量高效**：Express 是 Node.js 最成熟的 Web 框架，中间件生态丰富，适合 API 服务场景
- **成熟稳定**：mysql2 驱动支持连接池、参数化查询（Prepared Statements），天然防 SQL 注入
- **缓存加速**：Redis 用于缓存热点数据（审批列表、用户信息）、会话管理、限流计数，可显著降低 MySQL 查询压力
- **社区支持**：三者均为业界标准方案，文档丰富，遇到问题可快速找到解决方案

**潜在瓶颈：**
- Node.js 单线程模型下 CPU 密集型操作（如 Excel 导出、图片处理）会阻塞事件循环 → 通过 Worker Threads 或拆分独立服务解决
- MySQL 单库写入压力 → 初期用户量较小（<1000 人）无瓶颈，后期可通过读写分离优化

**评估结论：** ✅ **技术方案可行**，完全满足 OA 系统需求

## 4. Redis 部署方案

### 4.1 安装 Redis（Ubuntu 24.04）

```bash
# 远程执行安装脚本
ssh root@111.229.107.123

# Step 1: 更新包列表并安装 Redis
apt update

# Step 2: 验证安装
redis-server --version

# Step 3: 启动并设置开机自启
systemctl start redis-server
systemctl enable redis-server
systemctl status redis-server
```

### 4.2 Redis 安全配置

编辑 Redis 配置文件 `/etc/redis/redis.conf`：

```bash
# 备份原始配置
cp /etc/redis/redis.conf /etc/redis/redis.conf.bak

# 修改以下配置项
```

**关键配置项修改：**

| 配置项 | 建议值 | 说明 |
|--------|--------|------|
| `bind` | `127.0.0.1` *(推荐)* 或 `0.0.0.0` | 开发阶段建议绑定本地；如需远程访问 |
| `port` | `6379` | 默认端口 |
| `requirepass` | 设置强密码 | 开发阶段可先不设密码 |
| `maxmemory` | `256mb` | 根据服务器内存调整 |
| `maxmemory-policy` | `allkeys-lru` | 内存满时淘汰策略 |
| `appendonly` | `yes` | 开启 AOF 持久化 |

**推荐安全配置：**

```bash
# Node.js 后端与 Redis 同服务器时，绑定本地地址最安全
sed -i 's/^bind .*/bind 127.0.0.1/' /etc/redis/redis.conf

# 设置密码（按需，开发阶段可先注释）
# sed -i 's/^# requirepass .*/requirepass YourRedisPassword2024/' /etc/redis/redis.conf

# 限制最大内存
sed -i 's/^# maxmemory .*/maxmemory 256mb/' /etc/redis/redis.conf
sed -i 's/^# maxmemory-policy .*/maxmemory-policy allkeys-lru/' /etc/redis/redis.conf

# 开启 AOF 持久化
sed -i 's/^appendonly no/appendonly yes/' /etc/redis/redis.conf

# 重启 Redis 使配置生效
systemctl restart redis-server
```

### 4.3 验证 Redis 连接

```javascript
// 伪代码示例：Redis 不可用时的降级处理
async function getFromCache(key) {
```

## 5. 旧版 users 表复用方案

### 5.1 表结构确认

> ⚠️ **注意：** 由于当前环境无法直接连接 MySQL 读取旧表结构，以下方案基于项目已知信息制定。建议开发前先执行以下命令确认表结构：

```bash
# 连接服务器查看旧版 users 表结构
mysql -u daily_report_user -p<YOUR_DB_PASSWORD> -h <YOUR_SERVER_IP> daily_report -e "DESCRIBE users;"

# 同时查看表创建语句，了解索引和约束
mysql -u daily_report_user -p<YOUR_DB_PASSWORD> -h <YOUR_SERVER_IP> daily_report -e "SHOW CREATE TABLE users\G"
```

### 5.2 新旧 users 表映射方案

**方案选择：数据同步方案（推荐）**

| 对比项 | 方案 A：视图/直连（轻量） | 方案 B：数据同步（推荐） | 方案 C：全新用户表 |
|--------|--------------------------|------------------------|-------------------|
| 方案说明 | 新表为 VIEW，直接映射旧表 | 新建完整 users 表，首次脚本导入 | 完全新建用户体系 |
| 数据一致性 | 实时同步 | 一次性同步后各自维护 | 无需兼容旧数据 |
| 开发复杂度 | 低（SQL 视图即可） | 中（需写迁移脚本） | 低 |
| 扩展灵活性 | 差（受限于旧表结构） | 好（可按需扩展字段） | 最好 |
| 微信集成 | 需改造旧表或加字段 | 新表完整支持 | 新表完整支持 |
| 推荐度 | ⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ |

**推荐方案：方案 B — 数据同步**

选择理由：
1. OA 系统新增微信登录等能力，需要 `openid`、`avatar_url`、`role` 等新字段，旧表难以扩展
2. 新表按 OA 需求独立设计，不受旧表结构约束
3. 首次通过迁移脚本从旧库导入基础数据（用户名、密码等），后续各自维护
4. 旧库 `daily_report` 变为只读数据源，不再写入

### 5.4 数据迁移脚本

```javascript
// scripts/migrate-users.js（示意）
const mysql = require('mysql2/promise');

async function migrateUsers() {
  // 1. 连接旧库
  const oldConn = await mysql.createConnection({
    host: '111.229.107.123',
    user: 'daily_report_user',
    password: process.env.OA_DB_PASSWORD,
    database: 'daily_report',
  });

  // 2. 连接新库
  const newConn = await mysql.createConnection({
    host: '111.229.107.123',
    user: 'daily_report_user',
    password: process.env.OA_DB_PASSWORD,
    database: 'wx_app_oa',
  });

  // 3. 读取旧用户
  const [oldUsers] = await oldConn.execute('SELECT * FROM users');

  // 4. 逐条导入（并可生成新的 user_id）
  for (const user of oldUsers) {
    await newConn.execute(
      `INSERT INTO users (user_id, username, nickname, phone, email, department, role, status, password_hash, created_at, updated_at)
       VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, NOW(), NOW())`,
      [
        `U${String(user.id).padStart(5, '0')}`,
        user.username || null,
        user.nickname || user.username || null,
        user.phone || null,
        user.email || null,
        user.department || null,
        'employee',
        'active',
        user.password || null,
      ]
    );
  }

  console.log(`迁移完成：共导入 ${oldUsers.length} 个用户`);
  await oldConn.end();
  await newConn.end();
}

migrateUsers().catch(console.error);
```

## 7. 风险点与缓解措施

### 7.1 风险矩阵

| 风险编号 | 风险描述 | 概率 | 影响 | 等级 | 缓解措施 |
|----------|----------|------|------|------|----------|
| R1 | Node.js 版本不满足 18.x LTS | 低 | 高 | 🟡 中 | 提前确认，使用 nvm 切换版本 |
| R2 | Redis 安装失败或版本过旧 | 低 | 中 | 🟢 低 | 从源码编译安装，或使用 Docker 部署 |
| R3 | MySQL 远程连接被防火墙阻断 | 中 | 高 | 🟡 中 | 确认安全组规则开放 3306 端口；或通过 SSH 隧道连接 |
| R4 | 旧版 users 表字段与新表不兼容 | 中 | 中 | 🟡 中 | 迁移脚本中加入字段映射表，手动处理异常数据 |
| R5 | 服务器磁盘空间不足（日志增长） | 低 | 中 | 🟢 低 | 配置日志轮转（按天/按大小），设置保留天数 |
| R6 | 高并发下 MySQL 连接池耗尽 | 低 | 高 | 🟡 中 | 设置合理连接池上限，引入 Redis 缓存减少查询 |
| R7 | 微信小程序 AppSecret 泄露 | 低 | 高 | 🟡 中 | AppSecret 仅存 `.env` 不提交 Git，服务端控制调用 |
| R8 | 生产环境 ICP 备案未通过 | 高 | 高 | 🔴 高 | 开发阶段使用 IP + 端口部署，小程序端使用 localhost 或 IP |

### 7.2 关键风险应对方案

#### R3：MySQL 远程连接被阻断

```bash

# 方案 B：通过 SSH 执行 MySQL 命令（不需开放 3306 端口）
```
