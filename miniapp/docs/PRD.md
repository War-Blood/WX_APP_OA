## 1. 产品概述

### 1.1 产品背景

中小微企业在数字化转型过程中面临以下核心痛点：

- **办公碎片化**：审批、日报、任务、公告分散在不同工具（微信、钉钉、邮件、Excel），信息割裂严重
- **管理透明度低**：日报靠微信群接龙，审批靠口头传达，管理者无法实时掌握团队工作进度
- **部署成本高**：传统OA系统部署复杂、费用高昂，不适合中小微企业的轻量化需求
- **移动办公刚需**：一线员工（施工、运维、销售等）以移动端为主要工作设备，缺乏适配的移动办公工具
- **数据孤岛**：项目进度、人员考勤、资产状态等数据无法打通，决策缺乏数据支撑

### 1.2 产品定位

**智慧办公助手**是一款基于微信小程序的轻量化OA办公系统，定位为：

- **零部署、即开即用**：依托微信生态，无需下载安装，扫码即可使用
- **核心办公场景全覆盖**：聚焦审批流程、日报管理、任务协作、项目管理、资产台账、公告通知六大核心场景
- **模块化、可扩展**：采用前后端分离架构，模块间低耦合，支持按需启用功能模块
- **角色化视角**：提供员工端与管理端两套操作界面，权限分明，操作简洁
- **数据驱动管理**：通过日报数据、项目进度、审批统计等为管理者提供决策依据

### 1.3 目标用户

| 用户角色 | 职责描述 | 核心需求 | 用户规模预期 |
|---------|---------|---------|------------|
| **普通员工** | 一线执行人员，需每日汇报工作、发起审批、查看任务 | 日报填写与提交、审批发起、任务查看、个人数据查询 | 80% |
| **部门主管/项目经理** | 中层管理者，需审核日报、审批申请、跟踪项目进度 | 日报审核、审批处理、任务分配、项目进度查看 | 15% |
| **企业管理员** | 高层管理者/系统管理员，需用户管理、权限控制、全局数据查看 | 用户权限管理、全局审批、数据统计、系统配置 | 5% |

### 1.4 核心价值主张

| 价值维度 | 具体体现 |
|---------|---------|
| **效率提升** | 日报填写模板化，审批流程自动化，减少沟通成本 60%+ |
| **管理透明** | 日报提交率、审批时效、项目进度数据实时可视化 |
| **成本节约** | 零部署成本，无需硬件投入，基于微信现有生态 |
| **决策支持** | 日报数据分析、审批统计、项目进度报表为管理决策提供依据 |
| **体验统一** | 一个入口完成所有办公操作，告别多工具切换 |

### 1.5 产品范围

#### 1.5.1 核心功能（P0 — 必须实现）

- 用户登录与身份认证
- 工作台（首页）：快捷入口、待办提醒、数据概览
- 审批流程：发起审批、审批中心、审批详情
- 日报管理：日报填写、提交、审核、历史查询
- 消息通知：审批/日报/任务消息推送
- 个人中心：个人信息、我的数据、设置

#### 1.5.2 重要功能（P1 — 建议实现）

- 任务管理：任务看板、任务分配、进度跟踪
- 项目管理：项目列表、项目详情、项目成员管理
- 资产管理：资产台账、领用/归还、资产盘点
- 公告系统：企业/部门两级公告、发布管理

#### 1.5.3 增值功能（P2 — 可选实现）

- 高级审批：并行审批、加签/转签、条件审批
- 数据报表：甘特图、工时统计、效率分析
- 考勤管理：签到打卡、请假/加班申请
- 文档管理：在线文档、文件共享

## 2. 功能需求

### 2.1 用户认证与权限模块

#### 2.1.1 功能描述

提供安全、便捷的用户认证体系，支持微信生态一键登录，并基于角色实现细粒度的权限控制。

#### 2.1.2 功能列表

| 功能编号 | 功能名称 | 功能描述 | 优先级 | 用户角色 |
|---------|---------|---------|-------|---------|
| AUTH-01 | 微信一键登录 | 通过微信授权获取用户信息（昵称、头像），自动注册/登录 | P0 | 全部 |
| AUTH-02 | 手机号绑定 | 可选的手机号验证绑定，用于账号找回和多端登录 | P2 | 全部 |
| AUTH-03 | Token 管理 | 基于 JWT 的登录态管理，Token 自动刷新，过期自动跳转登录 | P0 | 全部 |
| AUTH-04 | 角色权限控制 | 基于 RBAC 模型，定义员工/管理员/超级管理员三级角色 | P0 | 全部 |
| AUTH-05 | 用户管理 | 管理员可查看用户列表、设置管理员权限、禁用/启用账号 | P0 | 管理员 |
| AUTH-06 | 页面路由守卫 | 根据用户角色自动拦截未授权页面访问，跳转到对应首页 | P0 | 系统 |

#### 2.1.3 认证流程

```
[用户打开小程序] → [检查本地 Token] → [Token 有效] → [进入首页]
                                         ↓
                                    [Token 过期/不存在]
                                         ↓
                              [调用 wx.login 获取 code]
                                         ↓
                              [请求后端 /api/login 接口]
                                         ↓
                              [后端返回 openid + Token]
                                         ↓
                              [缓存 Token + 用户信息]
                                         ↓
                                    [进入首页]
```

#### 2.1.4 权限矩阵

| 功能模块 | 普通员工 | 部门主管 | 企业管理员 |
|---------|---------|---------|-----------|
| 日报填写/提交 | ✓ | ✓ | ✓ |
| 日报审核 | - | 本部门 ✓ | 全局 ✓ |
| 审批发起 | ✓ | ✓ | ✓ |
| 审批处理 | - | 本部门 ✓ | 全局 ✓ |
| 任务查看 | 本人 ✓ | 本部门 ✓ | 全局 ✓ |
| 任务分配 | - | ✓ | ✓ |
| 用户管理 | - | - | ✓ |
| 项目查看 | 参与项目 ✓ | 本部门 ✓ | 全局 ✓ |
| 资产管理 | 本人领用 ✓ | 本部门 ✓ | 全局 ✓ |
| 公告发布 | - | 本部门 ✓ | 全局 ✓ |

```
[草稿] ──→ [已提交/待审核] ──→ [已通过]

#### 2.3.4 日报表单字段定义

**通用日报字段：**

| 字段 | 类型 | 必填 | 说明 |

| blockers | String | 否 | 遇到的问题/风险 |
| remarks | String | 否 | 备注说明 |
| attachments | Array | 否 | 附件列表（图片），最多 9 张 |

**项目进度日报额外字段：**

| 字段 | 类型 | 必填 | 说明 |
|-----|------|-----|------|
| projectName | String | 是 | 项目名称 |
| projectArea | String | 否 | 施工区域/地点 |
| relatedUnit | String | 否 | 相关单位 |
| workerInfo | Object | 否 | 人员信息（姓名、人数） |
| machineModel | String | 否 | 设备型号 |
| workContent | String | 是 | 当日工作内容 |
| progress | Number | 是 | 当前总进度百分比 (0-100) |
| todayWorkSummary | String | 是 | 今日工作总结 |
| tomorrowWorkContent | String | 是 | 明日工作安排 |
| workType | String | 否 | 工作类型（工作/待工） |

| 审批类型 | 特有字段 | 说明 |

#### 2.4.4 审批流程设计

```
[发起审批] → [选择审批人] → [提交申请]

                                ↓
                    ┌──── 通过 ────┐ └──── 驳回 ────┘
                    ↓                           ↓
              [审批完成]                  [申请已驳回]

#### 2.10.4 模块接口定义

每个业务模块通过 `services/` 层封装 API 调用，对外暴露统一接口：

```
Module Interface {
  getList(params)     → Promise<{ list, total, page }>
  getDetail(id)       → Promise<DetailObject>
  submit(action, data) → Promise<Result>
}

扩展新模块需：
1. 在 services/ 下创建新的服务文件
2. 实现上述标准接口
3. 在 config/index.js 中注册 API 路径
```

#### 2.10.5 可扩展性设计原则

| 原则 | 说明 | 实现方式 |
|-----|------|---------|
| 单一职责 | 每个模块只负责一个业务领域 | pages/services/components 按功能拆分 |
| 开闭原则 | 对扩展开放，对修改关闭 | 策略模式（request.js）、工厂模式（component-factory.js） |
| 接口隔离 | 模块间通过接口通信 | services 层统一封装 API，页面不直接调用 request |
| 依赖倒置 | 高层模块不依赖低层模块 | 页面依赖 services 抽象层，不依赖具体实现 |
| 模块自治 | 模块可独立开发、测试、部署 | 每个页面/组件有独立的 js/json/wxml/wxss |
