# 技术规范文档

> 本文档定义了「智慧办公助手（OA办公小程序）」的技术选型、架构规范、设计系统和开发标准。
> 基于 PRD.md、UI-Design.md、Pixso 设计稿共同确认。

---

## 1. 技术选型决策（已确认）

| 决策项 | 选择结果 | 说明 |
|--------|---------|------|
| **开发框架** | uni-app（Vue 3 + Vite） | 全量迁移，替代原生微信小程序框架（.wxml/.wxss 转为 .vue） |
| **UI 组件库** | uni-ui（DCloud 官方） | 轻量级、与 uni-app 深度集成、维护稳定 |
| **状态管理** | Vue 3 Composition API + Pinia | Vue 3 响应式系统 + Pinia 状态管理库 |
| **TabBar** | uni-app 内置 tabBar | 原生体验，在 pages.json 中配置 |
| **主题色** | #2B6DE8 高效蓝 | 与 UI-Design.md 和 Pixso 设计稿一致 |
| **字体** | Noto Sans SC → 系统字体 | 设计稿使用 Noto Sans SC，代码 fallback 到系统字体 |
| **后端策略** | 本地 VM Mock → 生产部署 | 先在本地虚拟机通过 Mock 数据调通，再对接 https://warblood.online |
| **构建工具** | Vite（uni-app 默认） | 基于 Vite 的 uni-app 构建方案 |

### 1.1 框架迁移要点

```
原生小程序 → uni-app (Vue 3)
  .wxml      →  <template> 模板
  .wxss      →  <style> + CSS变量
  .js (Page) →  <script setup> + definePageConfig
  .json      →  pages.json 统一管理
```

- 项目结构由原生 `pages/每个页面独立目录` 转为 uni-app `src/pages/` 结构
- 全局变量使用 Pinia store 替代 app.globalData
- 页面路由在 pages.json 中统一配置
- uni-app 条件编译保留扩展可能性（H5/App端）

### 3.2 组件开发规范

**组件命名规范：**
- 目录名：kebab-case（如 `status-tag`）
- 文件名：`index.vue`（uni-app 单文件组件）
- 组件名：多单词 PascalCase（`StatusTag`）

**组件接口规范：**
- props 必须定义 type 和默认值
- 事件通过 `emit` 向上传递
- 样式使用 `scoped` 隔离
- 遵循设计系统的 CSS 变量体系

**组件创建优先级（已确认）：**
1. L4 弹窗组件优先（P0 核心）：confirm-dialog, action-sheet, opinion-input, date-picker, image-uploader, person-picker
2. L2/L3 页面组件按需创建：stat-card, search-bar, timeline, tab-bar-filter, quick-entry, notice-board, chart-ring

### 3.3 状态管理规范

- 使用 **Pinia** 管理全局状态
- **user store**：用户信息、登录态、角色权限
- **app store**：全局 UI 状态（主题、通知数）
- 页面级状态使用 Vue 3 Composition API（`ref`/`reactive`）
- 避免在 store 中存储组件样式相关的数据

### 3.4 页面开发规范

**页面开发顺序（已确认）：按功能模块垂直开发**

```
阶段1：用户认证模块 → 登录页
阶段2：工作台模块 → L1-1首页 + L1-2功能中心 + L1-3个人中心
阶段3：审批模块 → L2-01审批中心 + L3-01审批详情 + L3-02发起审批
阶段4：日报模块 → L2-06日报历史 + L3-06日报详情 + L3-07日报编辑 + L3-08驳回编辑
阶段5：消息模块 → L2-02消息中心 + L3-03消息详情
```

### 3.6 组件封装与前端 SDK 设计规范

#### 3.6.1 设计目标

- **页面瘦身**：单个 .vue 文件不超过 300 行（模板 + 脚本 + 样式总和），超过必须拆分为子组件
- **关注点分离**：UI 渲染、业务逻辑、数据请求三层分离，互不混写
- **高复用性**：同一 UI 模式出现 2 次以上必须提取为公共组件
- **低耦合**：组件间不直接引用，通过 props/emit/slot 通信

#### 3.6.2 组件封装原则

| 原则 | 说明 | 违规示例 |
|------|------|---------|
| **单一职责** | 一个组件只做一件事，拆分到原子级（按钮→图标按钮→带文字图标按钮） | 一个组件既显示用户头像又拉取审批列表 |
| **接口最小化** | props 不超过 5 个，超过则考虑拆分子组件或使用 default/object 聚合 | `props: { title, desc, icon, color, size, bg, ... }` |
| **状态内聚** | 组件内部状态不下沉到父组件，通过 emit 通知父组件结果 | 父组件定义 ref 来控制子组件内部展开/收起 |
| **无副作用** | 组件不直接调用 API、不操作 localStorage、不修改全局样式 | 组件 mounted 中直接 `uni.request()` |

**组件层级分类：**

| 层级 | 说明 | 示例 | 存放位置 |
|------|------|------|---------|
| **原子组件** | 最小 UI 单元，无业务逻辑 | `Button`, `Icon`, `Badge`, `Tag` | `src/components/` |
| **分子组件** | 组合原子组件，含少量业务逻辑 | `StatusTag`, `StatCard`, `QuickEntry` | `src/components/` |
| **业务组件** | 绑定具体业务数据，可独立渲染 | `ApprovalCard`, `ReportCard` | `src/components/` |
| **页面组件** | 由业务组件组合而成，负责页面布局 | `home/index.vue` | `src/pages/` |

**拆分触发条件（满足任一即拆分）：**
- 模板中 `v-for` 循环渲染的区块 → 提取为列表项组件
- 带有独立交互逻辑的区域（点击、滑动、输入） → 提取为独立组件
- 超过 20 行 CSS 的样式块 → 考虑是否组件拆分不合理
- 同一个数据请求结果被多处使用 → 提取为 composable（组合式函数）

#### 3.6.4 SDK 分层设计

**禁止在页面中直接调用 `uni.request` 或 `uni.xxx API` 操作数据**，必须通过 SDK 层封装：

```javascript
// src/services/ 目录分层
services/
├── request.js          // HTTP 请求基类（统一拦截、错误处理、Token刷新）
├── modules/            // 按业务模块拆分的 SDK
│   ├── auth.js         // 认证模块：login(), logout(), refreshToken()
│   ├── report.js       // 日报模块：getList(), getDetail(), submit(), review()
│   ├── approval.js     // 审批模块：getList(), getDetail(), create(), approve()
│   ├── message.js      // 消息模块：getList(), getUnreadCount(), markRead()
│   ├── project.js      // 项目模块：getList(), getDetail(), createTask()
│   ├── user.js         // 用户模块：getProfile(), updateProfile()
│   └── index.js        // 统一导出
└── utils/
    ├── storage.js      // 缓存工具（封装 uni.getStorageSync）
    ├── router.js       // 路由工具（封装 uni.navigateTo/redirectTo）
    └── format.js       // 数据格式化工具
```

**SDK 调用规范：**

```javascript
// ❌ 错误：页面直接调用 API
const res = await uni.request({ url: '/api/report/list' })
if (res.data.code === 0) {
  list.value = res.data.data
}

// ✅ 正确：通过 SDK 调用
import { reportApi } from '@/services'

const data = await reportApi.getList({ page: 1, size: 20 })
list.value = data
```

**Composable（组合式函数）模式：**

将可复用的业务逻辑提取到 `src/composables/` 目录：

```javascript
// src/composables/useReportList.js
import { ref, onMounted } from 'vue'
import { reportApi } from '@/services'

export function useReportList() {
  const list = ref([])
  const loading = ref(false)

  async function fetchList(params) {
    loading.value = true
    try {
      list.value = await reportApi.getList(params)
    } finally {
      loading.value = false
    }
  }

  onMounted(() => fetchList())

  return { list, loading, fetchList }
}

// 页面中使用
import { useReportList } from '@/composables/useReportList'
const { list, loading } = useReportList()
```

#### 3.6.6 TabBar 组件的标准化封装

#### 3.6.7 代码复用检查清单

在提交代码前，对照以下清单检查是否需要封装：

- [ ] 同一段 HTML 结构是否出现了 2 次以上？ → 提取为组件
- [ ] 同一段 JS 逻辑是否在多个页面重复？ → 提取为 composable
- [ ] API 调用是否直接在页面中编写？ → 迁移到 services/modules/
- [ ] 组件 props 是否超过 5 个？ → 拆分或合并
- [ ] 页面 .vue 文件是否超过 300 行？ → 拆分
- [ ] 样式类名是否存在硬编码色值？ → 使用 CSS 变量
- [ ] 是否有多个页面使用相同的样式模式？ → 提取为全局样式 mixin
